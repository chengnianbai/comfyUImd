## 一、一句话结论

**侧脸糊不是提示词问题，是「参考图与目标视角不匹配」——Kontext 的 `ReferenceLatent` 是软条件，
参考图是正脸而目标是 90° 侧面时，它只能传身份、传不了毛孔级高频，模型只能退回"90° 侧面=光滑"的先验。**
重构后的链路把「姿势」交给 Kontext、「质感」交给 SDXL，并用**像素对齐参考**做质感重绘。

## 二、诊断（全部有量化证据，不靠印象）

### 2.1 建立了度量标尺（重要：这个指标只用于**同一引擎内**比较）

皮肤掩膜内的拉普拉斯方差 `lapVar` / 局部标准差 `locStd`，统一归一到 **880×1184** 再比：

| 图 | lapVar | locStd | 出处 |
|---|---|---|---|
| ★ `闻灯-正脸-已确认_成品`（用户认可的稿） | **234.81** | 3.897 | 脸部素材集 |
| Kontext 正脸（重构前） | 198.79 | 3.402 | `live_front_00029` |
| Kontext 90° 侧脸（重构前） | 150.27 | 3.066 | `live_left_00045` |
| v23 自己的侧脸成品 | 139.94 | 2.811 | 脸部素材集 |
| 身份锚 `00009` | 106.92 | 2.394 | input/ |

★ **教训：这个指标测的是"微对比度"，不是"像不像真皮肤"**。
用户认可的 P45（95.79）指标更低但观感更好；它只能当辅助，**最终以目视为准**。

### 2.2 侧脸糊的根因（决定性反证）

侧脸的参考图（正脸产物 lapVar 198.8）**比侧脸自己的输出（150.3）还细**——
参考更好、结果反而掉了 ⇒ 是「重投影成 90°」这个**任务本身**在压制高频，不是参考图不够好。

### 2.3 三个真 bug（都已修）

| # | Bug | 证据 |
|---|---|---|
| 1 | 组2 节点 `1004` 加载的是 `wendeng_v23_face_base.png`（lapVar **117.44**），**不是**那张认可稿（`wendeng_face_base.png`，**234.82**，与认可稿降到 896 后逐位一致） | 两文件测得 117 vs 235 |
| 2 | 线上计数器 `last_link_id` 过期（写 2318，实际已存在 id=2319 的连线）→ 我生成的连线 id 撞号，把 `1033.latent` 挤成 IMAGE、类型报错 | 提交验证时暴露 |
| 3 | `_scripts/wf_api.py` 的 UI→API 转换**不检查 `mode`** → 界面里"禁用"的节点在 API 提交路径上照样执行（三个中间存图节点禁用了却还在落盘） | 已在 `to_api()` 加 `mode==2 → 跳过` |

### 2.4 内眼角肉瘤

- **根因：基图 `wendeng_face_base.png` 本身**右眼内眼角就带一个粉肉色隆起，L2/L3 全部继承。
- 排除过程：纯 SDXL 正脸 → 有；Kontext 提质感段 `d1.0` 会**放大**它；`d0.93 + 参考 latent` 会**减弱**它；
  在 `d1.0` 下加"内眼角干净"的正向词**无效**（cfg=1.0，那一遍的负向完全失效）。
- 结论：**只能修基图**（模型侧改不动）。

### 2.5 肤色差

正脸 R/G = **1.258**，侧脸 1.236（正脸更黄 1.8%）。
把正脸提质感也对齐到 `0.93` 后变成 1.205（**方向反了**）⇒ 肤色差**不在提质感那一档**，
而在上游两张来源图（`wendeng_face_base.png` 与 Kontext 90°）本身的色差。**未解决，待办。**

## 四、关键实测数据（可复现）

### 4.1 「对齐参考」机理（本次重构的理论基础）

| 实验 | 参考图 | 结果 |
|---|---|---|
| A：只换参考为"侧脸自己"、提示词一字不改、d1.0 | 侧脸自身 | lapVar 150.27 → **191.11**，与基线像素差仅 **2.2%** |
| B：A + "要毛孔"的重拍词 | 侧脸自身 | → **222.25** |

⇒ **参考图与目标视角像素对齐时，Kontext 只重绘表面、姿势几乎不动。**

### 4.2 Kontext 提质感段是一个"放大器"（denoise 只有两档有用）

参考图 lapVar 与输出 lapVar 的关系（均归一 880×1184）：

| 参考图 | 参考 lapVar | 输出 lapVar | 放大倍数 |
|---|---|---|---|
| 「锚=00009」时代的左脸 | 119.79 | **271.21**（用户认可） | ×2.26 |
| 「锚=SDXL正脸」时代的左脸 | 172.82 | **566.38**（过火／像变脸） | ×3.28 |

`denoise` 扫描（参考固定 172.82）：

| denoise | 起点 | 输出 |
|---|---|---|
| 0.60 | 参考 latent | 87.51（磨皮） |
| 0.75 / 0.85 / 0.93 | 参考 latent | 154 / 153 / **157**（几乎不干活） |
| 1.00 | 纯噪声 | **566.38**（过火） |

⇒ **双峰：`f<1.0` 结构被锚住就不干活；`f=1.0` 一开就是 ×3.3。没有"温柔加强"档。**
⇒ 用户选定 **`0.93`**（当前线上）；它同时也是让内眼角肉瘤减弱的那一档。

### 4.3 已证伪的路线（别再走）

| 路线 | 实测结果 |
|---|---|
| 细节 LoRA（`FLUX.1-dev-LoRA-add-details`） | 正权重单调**削弱**质感（+0.70 时 locStd 3.066→2.852）；负权重 −1.0 直接出伪影 |
| SDXL 从正面 img2img 转 90° | 到不了：T2I-Adapter(canny) 强度 1.5→3.5 姿势**纹丝不动**只变脏 |
| SDXL 重绘一张真 90° 侧脸 | **任何 denoise 都把它拧回 3/4**（d0.30 就已改动 26.8% 像素；正脸 vs 侧脸这种整姿势差是 57.3%） |
| 把提质感输入从"放大后 1108"换成"放大前 1105" | 无效（553.98 vs 566.38）：`FluxKontextImageScale` 会把两者归一到同尺寸，UltraSharp 的锐化被降采样抹掉 |

## 五、模型/环境事实（本次新确认）

- **`FLUX1\flux1-schnell.safetensors` 的内容是 Kontext fp8**——借白名单槽位名落盘，**勿"修正"文件名**。
- Manager `install_model` 用 **`(save_path, base, filename)` 三元组精确匹配白名单**，不匹配直接 400。
  白名单里**没有** Flux 细节 LoRA 槽位 → 只能借槽位（如 `loras/HyperSD/FLUX.1/…`）。
  SDXL ControlNet / T2I-Adapter 槽位倒是齐全（`controlnet/SDXL/…`，真名可直接下）。
- `C:\ComfyUI\models` 是指向 **D 盘**的目录联接（junction）；C 盘紧张的真正原因是缓存/日志，不是模型本体。
- 实测下载速率（ModelScope）：**6.4 MB/s**（687MB 用 108 秒）。
- 该机**没有** MediaPipe 人脸关键点模型（`models/detection/` 为空）。
